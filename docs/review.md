# レビューの観点

PR をレビューするとき(人でも agent でも)に見ることです。上から順に重要です。
agent がレビューする場合も、approve と merge はしません。指摘をコメントで残し、判断は人がします。

## 1. 境界を緩めていないか(最優先)

このリポジトリが作るものは「制限」なので、制限を弱める変更がいちばん危険です。

- 既定の拒否が崩れていないか。書いていないものが許される経路ができていないか。
- 通信の規則が `audit` のまま適用されないか。`enforce` が抜けていないか。
- 宛先やパスに `*`、広すぎる glob が入っていないか。入れるなら、PR に理由があるか。
- ある namespace から、別の namespace の provider・サンドボックス・宛先を参照できるようになっていないか。
- agent が自分で `apply` したり、宣言を変えたりできる経路が増えていないか。
- 失敗したときに「制限なしで動く」方向に倒れていないか(失敗したら止まる方が正しい)。

## 2. 秘密情報

- 認証情報の値、token、鍵がコード・テスト・例・ログの出力に入っていないか。
- エラーメッセージや `plan` の出力に、値が出る経路がないか(名前だけを出す)。
- テストの固定値が、本物らしく見える値になっていないか(誤って本物と思われる・本物を貼る癖がつく)。

## 3. 設計との一致

- `docs/design.md` の「守る性質」を破っていないか。破るなら ADR があるか。
- OpenShell の書式やコマンドが `internal/openshell/` の外に漏れていないか。
- ADR の決定と、実装が食い違っていないか。食い違うなら、どちらを直すかが PR に書いてあるか。

## 4. 正しさ

- 宣言の検査に抜けがないか。境界の値(空の一覧、重複した名前、大文字小文字の違い、末尾の `/`)で正しく動くか。
- `plan` と `apply` が同じ差分を使っているか(見せたものと違うことをしない)。
- 途中で失敗したとき、どこまで適用されたかが分かり、もう一度流して直せるか。

## 5. テスト

- 変更した振る舞いにテストがあるか。境界を緩める方向の変更には、「緩めすぎていない」ことを示すテストがあるか。
- テストを消す・スキップする・期待値を合わせるだけの変更になっていないか。
- 本物の gateway が要るテストと、要らないテストが分かれているか。

## 6. 依存

- 足した依存の名前・バージョン・ライセンス・理由が PR にあるか。バージョンが固定されているか。
- OpenShell のバージョンを上げる PR は、変わった書式とその影響が書いてあるか。

## 7. 文書と PR

- 事実に「確認済み(出典)/ 未確認 / 推測」が付いているか。記憶だけで確認済みにしていないか。
- PR が 1 つの目的になっているか。関係のない変更が混ざっていないか。
- `AGENTS.md`、CI、`.github/` を変える PR のタイトルに `[rules]` が付いているか。

## 指摘の書き方

- 指摘には重さを付ける: **must**(merge の前に直す)/ **should**(直した方がよい)/ **nit**(好み)。
- 「何が起きるか」を具体的に書く(どんな入力・状態で、何が間違うか)。「危ないかも」だけで終わらせない。
- 確かめていない指摘は「未確認」と書く。
