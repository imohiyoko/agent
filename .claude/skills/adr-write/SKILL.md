# ADR を書く

## いつ書くか

- design.md の「守る性質」に触れる変更。
- 新しい外部の部品(OSS、サービス、実行方式)を土台にする変更。
- 認証・認可・通信・MCP・API の形を変える変更。
- 迷ったら書く。短くてよい。

## 手順

1. 番号: `ls docs/adr/` で一番大きい番号に 1 を足す。ファイル名は `NNNN-<英小文字とハイフン>.md`。
2. 下の型で書く。日本語、短い文。
3. `docs/adr/README.md` の表に 1 行足す(CI が確かめる)。
4. 既存の ADR を置き換えるなら、新しい ADR に「置き換えるもの」を書き、古い ADR の状態を `Superseded by NNNN` にする。
5. 状態は `Accepted` で出してよい(2026-11-23 に imohiyoko が「ADR は何も聞かなくていい、自由に実装して。その代わりドキュメントはちゃんと残すこと」と、決定を agent に任せた。AGENTS.md の 1 を見る)。「決めた人」には「agent(imohiyoko の委任、2026-11-23)」と書く。人が使いにくいと言ったら、その言葉と日付を書いて見直す。

## 型

```markdown
# ADR NNNN: <決定を 1 文で>

- 状態: Accepted
- 日付: YYYY-MM-DD
- きっかけ: <人の依頼、または困りごと>

## 要旨
- **困りごと**: ...
- **決定**: ...

## 決定
<具体的に。表を使ってよい>

## 確認の状態(YYYY-MM-DD)
- **確認済み**: ...(出典: 公式ドキュメント / ソースコード / 実行した結果)
- **未確認**: ...
- **推測**: ...

## 検討した代替案
| 案 | 利点 | 欠点 |

## 人が決めること(あれば)
```

## 注意

- 記憶だけで「確認済み」と書かない。外部の OSS はバージョンと確認日を書く。
- 限界(この決定で守れないこと)を必ず書く。
